# DSH 0.2.0-rc.2 适配说明（2026-10-10/11）

本仓库（huahua-dsh-chatroom）配套的聊天室链路，在 **DSH 0.2.0-rc.2** 下跑通所需的全部改动。

| 项 | 值 |
|---|---|
| 适配对象 | dsh-weave@0.1.0-rc.14 · dsh-chat@0.1.0-rc.33 · dsh-bridge@0.1.0-rc.15 · huahua-dsh-chatroom（本仓库） |
| 目标 | DSH 0.2.0-rc.2（Electron 44 / node 24.18.1） |
| 补丁入口 | patches/patch-adapt.ps1 -Package <weave|chat|bridge> -Root <包目录> [-DryRun] |

---

## 一、为什么会坏：0.2.0 的三处门槛

1. **RPC 注册需要 webServer**：0.2.0 里 connection.rpc.handle() 把 Fetch 路由注册在**调用方的 ctx** 上，未注入 webServer 就报 cannot get property "webServer" without inject。
2. **会话格式 v4 的 source 必须 producer-owned**：kind === "plugin" 是退休形态；第三方插件应写 plugin:<包名>，否则投递抛 format v4 message requires a producer-owned source kind。
3. **客户端服务 conversationEvents 已移除**：改用 uiConversation.events；桌面版启动审计会因 pending (waiting for service: conversationEvents) 直接拒绝启动。

## 二、逐包改动

### 2.1 huahua-dsh-chatroom（本仓库本体）

- inject 增加 webServer；新增 **lib/rpc-compat.js**：用 webServer.register({kind:"prefix"}) 自讲 0.1.x 的
  {type:"client-request"/"server-response"} 协议，并把 `{authority:"trusted-host"}` 换成 0.2.0 的 connection.requestRejection(req) 闸门。
- `PROFILE = "web"` 硬编码 → **installedProfileDir()**（按包的安装位置推导 profile 目录，linked/dev 安装回落到旧布局）。
- **1.1.0 新修**：上传**非 ASCII 文件名**出现双重编码（headers 按 latin1 读出 ⇒ 贺贝贝 → è´ºè´è´）。
  改为：优先 filename\*（RFC 5987，交 cleanFileName 做 percent 解码）；纯 filename 则对 latin1 字节做 UTF-8 复原。
  已加回归测试：上传 贺贝贝-测试.md ⇒ 响应与 manifest 的 name 必须等于原名。

### 2.2 dsh-weave（8 处，单文件 lib/index.js）

- 同上的 **webServer / rpc-compat** 适配。
- **激活即监听**：`apply()` 里直接 `weave.start()`（并 ticket()）。0.1.x 的写法是"等第一次外发才 bind"，
  重启后对端连不进来，现象是**对端 5/5 超时、session.catalog 恒空、端点状态反复** —— 极易误判成网络问题。
- 部署侧配置（bindAddr / identityPath / peersPath）**不属于补丁**，见第四节。

### 2.3 dsh-chat（10 处跨 4 文件 + 新增 lib/rpc-compat.js）

- **客户端半**：改用 ctx.get("uiConversation").events（并兜底旧名、try/catch + console.warn），否则整个 App 拒绝启动。
- **host 半 chat_send 守卫放宽**：判定为"本机成员 **或** room.linkedSessionId === sessionId"，
  否则 linked 房（我们是 remote 成员）直接抛 the current session is not a member of this room（capability 仍由 host 二次鉴权）。
- **房会话创建 sessions.create → agents.create**：`sessions.create()` 只造**进程内**会话、不 publish
  ⇒ 磁盘无 log ⇒ GUI resume 报 SessionPersistenceNotFoundError。改走平台路径
  `ctx.agents.create({sessionId, meta, agentOptions, seed})`（doc 里写的 rollback-covered publication），失败回落旧路径。
- **attach 竞态自愈**：`workspace.attachSession(id)` 返回 ok 但注册表被并发重写 ⇒ sessionIds 变空 ⇒ 入口可见但点不开。
  改为 attach 后**校验 sessionIds 是否含该 id**，不含则 250 ms 后重试一次（attach 幂等）。
- **link guard 降级**：linked/remote 成员的会话不带 room link 时只 warn（carries no room link; continuing without it），
  且**不写 make-up 事件**（避免污染时间线）。
- **过期会话 id 清理**：用 ctx.sessionPersistence.list() 建立 persistedSessionIds，逐房剔除已失效的 sessionId。
- 部署侧配置（store 路径）**不属于补丁**。

### 2.4 dsh-bridge（2 处）

- **投递 source**：`{kind:"plugin"}` → `{kind:"plugin:dsh-bridge", form:transport}`（门槛 2）。
- **cordis.patch.yml 行 id**：`dsh-bridge` → `huahua-dsh-bridge`，避免与 @wenbin_wb/dsh-bridge 同 id 触发双实例。

## 四、部署侧配置（重要，且不属于补丁）

三个包都必须在 profile 里**显式 pin 本机路径**（store 路径 / weave 身份与端口 / 文件服务端口与对外基址），
否则会去读写**另一份默认 home**，表现为"数据看不见 / 出现两个同名会话 / 两个实例各写一份 store"。
经实验，**把 config 写进包自带 cordis.patch.yml 的 insert 行**（而不是用户层 patch 再写一遍同名 id）可同时避免"双实例"。

### 一条踩过的硬规则（会话目录）

**不要重命名 sessions/ 下的任何名字。** 我们的真实事故：

    把 sessions/<slug>/<session-id>/ 目录改名成 ...archived-<ts>
    ⇒ 下次启动 assertStoredIdentity（用会话头 cwd+id 反推期望路径）判 corrupt session log
    ⇒ @deepseek-ai/dsh-workspace init 抛错 ⇒ workspaceRegistry 未注册
    ⇒ 11 行 pending（workspace-controller / session-controller / dsh-chat / dsh-weave / dsh-bridge ...）
    ⇒ 界面只报最末端的 "workspaceController 不可用 / 无法打开文件夹"

正确做法：

1. **不碰 sessions/ 里的任何名字**；
2. 要让 persistence 不再持有：把**整个会话目录搬到 sessions/ 根之外**、名字不变（根外不被 listArtifacts 扫描）；
   该做法已用隔离 home 做 A/B 验证（移出前后 未激活条目数 与 corrupt 字样完全一致）；
3. 只是"归档"：用 storages/workspace.json 的 **archivedSessionIds**（DSH 的正规归档只写标志位、不动目录名）。
