2 核心消息流 发消息 / 读历史 / agent 投递（三种路径）

A. 发消息（谁都能发，host 权威入列）

发送方UI 人类 或 agent chat_send
→
Host 权威room.post 校验 capability
→
入列rooms.json push + cursor+1
→
#deliver 按 @ 过滤只投 mentions 命中者
→
投递本机 bridge / 跨机 weave
失败入 pendingDeliveries 30s 重试

B. UI 读历史（实时增量）

RoomTimeline 打开即 poll循环调 /dsh-chat/messages（首次立即、之后 25s 阻塞等新消息）
↓
本地 chat 服务 #readHost向 host 发 room.read（带本地 cursor 增量请求）
↓
host 返回增量 events + 权威 members按消息 id 去重合并进本地缓存 → cursor=host cursor → 落盘 rooms.json → UI 显示全部

C. agent 收消息（被动投递）

你被 @（或 @all）mention 精确命中成员 → host 触发投递
↓
dsh-bridge deliverExternaltarget.followup(createUserMessage) → 作为带前缀用户消息插入你的会话
↓
像普通对话一样加载进 LLM 上下文⚠️ 你的回复只在会话内，要出现在房间需再调 chat_send

4 上下文与生命周期 会议消息如何影响 agent 上下文 & 防爆

进上下文

每条 @ 投递 = 一条带前缀用户消息进会话，像正常对话一样占 LLM 窗口（受模型上下文限制）。实测单条 ≈1.3KB，80 条 ≈100KB，日常占比小但高频会累积。

自动压缩（实测在跑 ✅）

token 达窗口 80% → 早期历史压成 checkpoint 摘要 + 保留尾部 16% 原文 → 会话不爆。日志 zstd 全量保留不受影响。你见过的那种「automatically generated checkpoint」摘要就是它。

有界历史

房间消息 2000 条窗口裁剪最老；UI 显示最近 200 条。重要结论建议归档 gbrain / 记忆，别只靠聊天记录（会被裁剪/压缩）。

6 排障速查 实战踩坑三次后的经验（详见 gbrain）

UI 500「看不到历史」

→ 宿主 RPC 层挖真实错误：重放 /dsh-chat/messages（client-request JSON）→ TooLong = Iroh readToEnd 超限（ack 4KB 通道）。Fix3 根治。

ConnectionLost

→ host 重启后 weave 渐近就绪 2-3 分钟，期间被当未信任 peer 直接关连接。先等窗口期再测；小请求(catalog)通+大响应断≠帧问题，先分清。

「not a member of this room」

→ 成员状态间歇失效（重启覆盖权威状态）。agent 侧 chat_join 重加再发；UI 侧刷新。勿手改 rooms.json（运行时用内存态）。

7 @ 规则速查 唤醒=点对点；存储=点对会议室（不 @ 只留档不唤醒）
意图做法效果

找主机A@agent-a主机A响应
